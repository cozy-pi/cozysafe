# ADR 0003: Sync between devices through the user's own cloud folder

Status: **Proposed** (2026-10-24, owner asked for real sync, not only backups)

## Context

Today a vault lives on one phone, with a one-file backup the person moves by hand
(`backup.rs`). The owner wants two phones (or a phone and a computer) to use the same
vault side by side: an item added on one shows on the other, edits and deletes follow.

What we have already makes this tractable:

- Every item is three independent blobs, `items/<bucket>/<id>.{meta,data,thumb}` (see
  "Layout on the device"), each AEAD-bound
  to the vault, the item and its role (`items.rs`). Nothing else holds vault state:
  tags are items, tag membership and favourites live in each item's record.
- Every record carries `modified_ms` and `deleted_ms` (trash).
- Opening a vault on another device needs only public files (`library.json`,
  `vaults/<id>/header.json`) plus the Secret Key (24 words) and the vault password.
  PIN and biometric files are per device and never leave it.

Constraints:

- The app promises "nothing goes to the internet" (decisions 2026-10-21). Sync breaks
  that promise, so it is **opt-in, off by default**, and the security page says so.
- No server of ours, no account of ours. Storage is the person's own cloud.
- The cloud must learn nothing beyond sizes, counts and timing (see Leaks).
- Pre-beta: formats may change, but the frozen backup must keep restoring.

## Decision

### Where: the person's cloud folder, behind one small trait

```rust
trait Remote {            // all paths relative to the vault's sync folder
    fn list(&self, dir: &str) -> Result<Vec<Entry>>;   // name, size, version tag
    fn get(&self, path: &str, out: &mut dyn Write) -> Result<()>;
    fn put(&self, path: &str, src: &mut dyn Read, if_absent: bool) -> Result<()>;
    fn delete(&self, path: &str) -> Result<()>;
    fn delete_many(&self, paths: &[String]) -> Result<()>;  // one batch where the place can
    fn parallel(&self) -> usize;                            // items sent at once (1: in turn)
}
```

Implementations (owner 2026-10-24: Google Drive and P2P):

1. **Local folder** (tests, desktop, and any folder a sync client already mirrors).
2. **Google Drive** (Android and iPhone): REST with the `drive.file` scope only (files
   this app created), so no access to the rest of the person's Drive. Needs an OAuth
   client and Google's consent screen review for that scope (to check before building).
3. **P2P**: two of the person's devices on the same Wi-Fi, no cloud at all. **Both open
   Sync → Sync with a nearby device and wait** (0.1.73, owner 2026-10-26): each listens and
   looks for the other on its own Wi-Fi (see "Finding the other device" below; iOS asks for
   Local Network access once), and once they found each other both screens ask "Sync with
   iPhone 15 Pro Max?" next to the same 3-digit number, as Bluetooth pairing does; the sync
   starts when both people tapped Sync. Nothing to type (0.1.66–0.1.72 had one device show
   three digits for the other to type). **Both devices must already hold the same vault**
   (same 24 words and vault password, owner 2026-10-24): P2P only syncs a vault both have
   opened; a new device restoring is the one exception, below (point 8). Every key comes
   from the vault's Master Key, so the channel only opens between devices that both have
   the vault, and a stranger on the Wi-Fi cannot join or even find one. The QR code stays
   for networks where looking does not get through. The peer
   serves its folder through the same `Remote` calls, so conflicts, journals and checks
   are the same code. Both apps must be open (iOS gives no background networking).
4. **iCloud Drive** later, if asked (needs the iCloud capability: infrastructure change).

### What: the same encrypted blobs, immutable

```text
<sync folder>/
  library.json                 copied as is (salt, Argon2 cost, Secret Key fingerprint)
  vaults/<vault id>/
    header.json                as is (wrapped Master Key for the password path)
    items/<id>.meta.<rev>      the sealed record, one file per revision
    items/<id>.data.<rev>      content of that revision (unchanged content: no new file)
    items/<id>.thumb.<rev>
    log/<device>/<n>           sealed change journal, append-only, per device
```

- **Nothing is overwritten.** A change writes new files with a new `rev` (random 128-bit
  hex) and then a journal entry; cloud folders give no atomic rename and two devices may
  write at once, so writes that never collide are the safe kind.
- The record gains `rev`, `base_rev` (the revision it was edited from) and `device`
  (random id of the device that wrote it). Additive, like `modified_ms` was.
- Old revisions leave the place 30 days after they were superseded (see "Old
  revisions").
- **An item deleted for good leaves the place** (owner 2026-10-24: 700 deleted photos
  stayed in Google Drive). Before telling the deletion, the device that deleted it
  removes the item's records and content written up to the deletion; a revision made
  later on another device stays, with its content. A device catching up finds the record
  gone and skips it (the journal's deletion follows). The first sync with a place after
  this change also cleans deletions told before it. Only places that can delete do it
  (Google Drive, a folder); a nearby device's session folder is thrown away anyway.
  The deletion keeps the last revision this device had (older than the deletion by its
  clock), so that record goes without being downloaded; any other revision is read and
  kept, with its content, when its `hlc` is newer than the deletion. Files go in batches
  of about 100, each batch's records before their content: a device catching up finds a
  record gone (and skips it), never a record whose content is gone.

### Layout on the device and on Google Drive

**Buckets.** An item's files are kept in a folder named by the last two hex digits of its
id, `00` to `ff` (`cs_vault::bucket_of`, the one place the rule lives). Item ids are
random, so each of the 256 buckets holds about 1/256 of the items, and no folder grows to
tens of thousands of files. A bucket is made when first needed and never removed.

**On the device:** `vaults/<vault>/items/<bucket>/<item>.{meta,data,thumb}`. Versions up
to 0.1.57 kept them flat in `items/`. Opening the vault moves each such file into its
bucket (one rename, same disk; content before records); a move cut short leaves every
file in one place or the other, files are read from either place until the move is done,
and the next open finishes it. A file already in its bucket is the newer one and the flat
copy goes. The index remembers when it is done. The backup format does not change: a
backup still names item files `vaults/<vault>/items/<item>.<ext>`; export takes them from
the buckets, import puts them back there.

**On Google Drive:** "Cozy Safe" holds one folder per vault, named by the vault's id:

```text
Cozy Safe/<vault>/index/<bucket>/<item>.<rev>             records/<item>/<rev>
Cozy Safe/<vault>/content/<bucket>/<item>.<rev>.<ext>     blobs/<item>.<rev>.<ext>
Cozy Safe/<vault>/log/<device>.<n>                        log/<device>/<n>
Cozy Safe/<vault>/lock/<name>                             lock/<name>
```

(right: the path in the sync layout, after `<vault>/`, which the sync engine still uses;
only the Drive transport knows the folders). A session lists everything the app can see
in one paged query (`trashed = false`, 1,000 a page: with `drive.file` that is only the
app's own files and folders), rebuilds each file's path from its folders, and keeps a
path → id index (sorted per vault; about 170 bytes a file, some 17 MB for 100,000
files). Folders are made when first needed, one request each, under a lock so items going
up at once never make two; should two devices still make the same folder, the first by id
is used and the other's files are moved into it. A device joining looks for vault folders
holding a lock.

**Earlier files on Drive** are moved into place when a session opens: files flat in "Cozy
Safe" named by their whole sync path (`<vault>/records/…`, up to 0.1.57), and files flat
in a vault's folder named by the rest (a layout never released). Each takes one `PATCH`
(`addParents`/`removeParents` and the new name), sent through the batch endpoint 100 at a
time; nothing is downloaded or sent again. Each move is one rename, so a move cut short
leaves every file in one place or the other, and the next sync goes on. A file found both
in place and elsewhere is the same file (files never change): the one in place is kept,
the other deleted. Files that are not the layout's are left alone.

### Old revisions

After a sync has sent this device's changes, and at most once a day per place, the
records of revisions superseded more than 30 days ago leave the place (only places that
can delete: Google Drive, a folder). A revision is superseded when the next newer one (by
`hlc`) was made; only items this device holds, at the revision the place has, are looked
at, and the other revisions' records are read for their clocks (unreadable ones stay).
Each is read once per place: its clock and content revision are kept in the local index
(`sync_rev_clock`, dropped when the revision leaves or the item goes).
The current revision and its content always stay, as does any revision newer than it
(another device's, not told yet). Content goes with the last revision that used it: a
content file shared by a revision that stays (same `data_rev`) stays. Records go before
content, in batches of about 100, counted in the Removing phase. A device that has not
synced for over 30 days finds the old records gone and takes the newer revision its
journal names (a missing record is skipped).

### Speed on Google Drive

Each Drive request is a round trip of 0.15 to 0.3 s, and one at a time that is most of a
sync's time (owner 2026-10-24: cleaning 764 deleted photos took about 10 minutes, four
requests each). So:

- **Items go up four at once** (`Remote::parallel`; a folder and a nearby device, one
  channel, stay at one). Each item's content goes before its record; the journal entry
  written every 50 items names only items whose files are all up, in the order they
  finished; progress counts items done. The first error stops the rest (those already
  under way finish) and the sync ends with it, Cancel included; the items not yet told
  go up again next time, already there files skipped.
- **Deletions go in batches**: Drive's batch endpoint takes 100 deletions in one
  request, each answer checked (deleted, or gone already; anything else fails the batch).
- **Records this device wrote are not read back** to be cleaned (above).

Together: cleaning a deleted photo costs a share of two batch requests instead of four
round trips, and sending many small items about a quarter of the time. Receiving stays
one item at a time.

### How devices learn about changes: per-device journals

Listing thousands of files on every sync is slow on Drive. Each device appends sealed
journal files `log/<device>/<n>` (Master Key, AAD = vault, device, n): "item X is now at
rev R". A device keeps, per other device, the last `n` it applied, and on sync lists only
`log/`, reads what is new, then fetches the records (and thumbnails) it names.
Content (`.data`) is fetched **on first open**, not up front: a new phone shows the whole
library in seconds and downloads a 2 GB video only when it is played. "Keep everything on
this device" is a setting.

A journal entry's `n` is strictly increasing and sealed: the cloud can withhold entries
(stalling), but cannot forge, reorder or replay them unnoticed.

### Conflicts

Each record keeps `rev`, `base_rev`, `device` and a **hybrid logical clock** `hlc`
(max of the device's clock and every `hlc` it has seen, plus one), so a phone with a
wrong clock cannot make its edits always win or always lose. The base revision's record
stays (until garbage collection) so merges are **three-way, field by field**:

| Case | Result |
|---|---|
| Different items | Both kept |
| Only one side changed the item | That change |
| Both changed, different fields (A renamed, B added a tag) | Both changes |
| Both changed the same field (name, favourite, tags) | Higher `hlc` wins; tags merge as sets (added on either side stays, removed on either side goes) |
| Both edited a note's text | The newer text stays; the other becomes a new note "<title> (from <device>)" — typed text is never lost |
| One moved to Recently deleted, the other edited | The edit wins: the item stays out of the trash |
| One deleted for good, the other edited | The edited item comes back (never lose data); the deleting side sees it return |
| A tag deleted while the other device tagged items with it | The tag comes back, since items still carry it |

**Deletions from elsewhere are held, not applied at once (2026-10-25).** A deletion for
good that arrives by sync does not remove the item here: its record moves to
`<id>.held` (sealed under the role `held`, so it can never pass for a live record), its
content stays, the deletion is recorded as usual and passed on. To sync the item is
gone (no `.meta`, no index row), so it is never sent back. Recently deleted lists it as
"Deleted on another device" for 30 days (purged then, or on Delete now). Restoring makes
a new revision, newer than the deletion, so every device takes it back. A newer revision
arriving from elsewhere replaces what was held. Backups carry live items only. Tags are
not held. Why: a trash emptied by mistake, or a phone in someone else's hands, must not
empty every device.

Photos, videos, recordings and files never change content after they are added, so
only notes can conflict on content. Every merge result is a new revision written by the
device that merged it, so all devices end with the same state.

### Joining another device

Settings → Sync → "Use on another device" shows nothing secret; on the new device:
choose the cloud → pick the Cozy Safe folder → type the 24 words and the vault password
(the same as restoring a backup) → set a PIN and Face ID for that device. Records sync
first, then thumbnails, content on demand.

### Engine placement

The engine lives in `cs-vault` (Rust), with the `Remote` trait; cloud transports are
platform code behind a channel (iCloud through `NSFileCoordinator`, Google Drive through
REST from Rust with the token handed in by the app). The local index (`vault.db`) gains
a `sync_state` table: per item the last synced `rev`, per remote device the last journal
`n`.

## P2P security (owner 2026-10-24: "security first, especially P2P")

Threats considered: someone on the same Wi-Fi watching, replaying, sitting in the middle
or pretending to be the other phone; someone who sees the QR code; a peer that sends
hostile requests; the network learning that a vault exists, or which devices hold it;
and, with several devices holding the vault, pairing with the wrong one.

1. **Only a device that holds the vault can join.** Both sides derive a pairing key
   from the vault's Master Key (`subkey(master, "p2p/v1/<vault id>")`). Knowing the QR
   code is not enough: without the vault, no message can be produced or read.
2. **Each wait is one-time and short-lived.** A waiting device makes a random 5-byte
   token (its id) for this wait only; the QR carries it, and a device that found this one
   reads it from the probe's answer (point 6). It works for one session and 5 minutes,
   then the device stops listening. Three failed handshakes also stop it. Of two devices
   that found each other, the one with the lower token connects and the other serves, so
   two devices never open two sessions to each other; a device never connects to its own
   token (nor knocks at its own address).
3. **Mutual proof with fresh nonces, no replay.** Hello with the joiner's nonce → reply
   with the host's nonce and a proof over both → the joiner's proof over both. Proofs are
   AEAD tags under a key from (pairing key, token); a recorded session cannot be
   replayed because each side's nonce is new. Session keys, one per direction, come from
   HKDF(pairing key, token, both nonces).
4. **Every frame sealed and numbered.** Length-prefixed frames, each XChaCha20-Poly1305
   with its direction and counter in the associated data: no reordering, replay,
   truncation or injection goes unnoticed; the first bad frame ends the session.
5. **What crosses is already encrypted.** Only sealed records and sealed blobs, the same
   bytes as on disk: even a broken channel would show no names or contents.
6. **Nothing is advertised.** No Bonjour/mDNS, no broadcast: the network never hears
   "Cozy Safe" or that a vault exists. A device listens only on its Wi-Fi address, on
   port 47823 (any port if that one is taken: then only the QR works), only while the
   sync screen is open and the app is in front.
   **Finding the other device (2026-10-25, both sides since 2026-10-26).** After the
   person allows it, each waiting device knocks every 3 seconds at port 47823 on each
   address of its own /24 (`a.b.c.1`–`254`) with a probe holding a fresh nonce. A waiting
   device answers with its own nonce and, for each key it holds (the vault's pairing key,
   and the Recovery Key's while "Help a new device restore" is on), a 16-byte tag from
   HKDF over both nonces that says "same vault", and its token hidden under a second such
   tag (XOR, the rest of the block zero and checked). A device lists only those whose
   first tag it can reproduce; a probe tells a stranger nothing (random-looking bytes,
   different every time, no name, no stable id) and does not count as a failed try.
   Bonjour was not used: it advertises a service name to the whole network, and raw
   multicast on iOS needs an entitlement Apple must grant. The knock is plain unicast TCP,
   which Local Network permission covers.
   **Several devices found.** None connects by itself. A short handshake with each (the
   same mutual proof as a session, mode "intro") swaps names inside the sealed channel,
   and the screen lists them; the person picks one. If the picked device holds the lower
   token, this one asks it, in another intro, to connect; otherwise this one connects.
   With exactly one found, the lower token connects at once. Names never travel in a
   probe's answer: only a device that proved the vault (or the 24 words, while the
   person allows restoring) learns them.
7. **A hostile peer gets nothing extra.** Requests are limited to this vault's current
   records and blobs by id; ids are checked (32 hex), sizes are capped (frames 1 MiB,
   streams in frames), and the session ends after 10 minutes idle.
8. **Restoring a device that has no vault yet.** It cannot derive the pairing key above,
   so it pairs with a key from the Recovery Key alone
   (`HKDF(secret key, "cozysafe/v1/p2p-restore")`), which the host derives from its
   library. The hello says which key is proven. After the handshake the host names the
   vault's id; the new device reads the vault's lock through the channel and opens it with
   the 24 words and the password ([`Library::join`]), then syncs the items in. Knowing
   the words without the password gets only sealed bytes, and only from a device that is
   unlocked, waiting on its sync screen with restoring allowed, its person watching the
   check number.
   **Consent (2026-10-25).** A host serves a restoring device only when the person
   turned on "Help a new device restore" on the waiting page (off by default, and it can
   be switched while waiting). While it is off, the host answers probes with random bytes in place of the Recovery Key's tags
   and refuses restore hellos and intros. When it is on, the new device (which only looks;
   it has no vault to serve) finds it like any device, and after the handshake and the
   names the host asks "Let iPhone 16 restore this vault?" next to the 3-digit check
   number both screens show; only Allow sends the vault's id and serves the vault; Don't
   allow, Cancel or no answer in 3 minutes tells the joiner the host stopped.
   Sync between devices that already hold the vault is unchanged. The lock read through
   the channel is checked like any other: an Argon2 cost below the phone floor is refused
   (ADR 0001).
9. **Both people confirm, comparing a number (numeric comparison, 2026-10-26).** After
   the mutual proof, each device tells the other its name (the model, "iPhone 15 Pro
   Max", never the name its owner gave it; cleaned of control and direction characters,
   40 characters at most), and both screens ask "Sync with …?" next to the same 3-digit
   number, `HKDF(pairing key, "session/check/" + token + both nonces) mod 1000`. Each
   answer crosses the sealed channel; nothing is served until both said Sync, a Cancel on
   either ends both at once ("Cancelled on the other device"), and no answer in 2 minutes
   is a Cancel. What the number proves: the two screens belong to the same session. A
   stranger cannot be in the middle at all (point 1), so the number is not what stops an
   attacker; it stops a mix-up between the person's own devices (several holding the
   vault, or a family member's phone that holds it too): only the device showing the same
   number is the one being synced. Three digits suffice for that (two sessions match by
   chance once in 1,000, and the person also sees the name). Why numeric comparison
   rather than typing a code (0.1.66–0.1.72): nothing to type or read out, the same
   protection, and both people agree rather than one.

10. **A hostile sync place (the cloud, or a peer) cannot roll content back or exhaust
   memory.** Each record seals the SHA-256 of its encrypted content and preview; fetched
   content must match or it is refused (the item key is the same across revisions, so
   older content would otherwise decrypt). Records and journal entries over 1 MiB are
   refused unread; journal entries are sealed with their device and number, so they
   cannot be renumbered, moved or made up. Paths may not hold `\\`, `:` or NUL, so
   nothing leaves the folder on Windows either.

Accepted: anyone on the same Wi-Fi can stop a pairing (connect and stall until the three
tries are used); they learn and change nothing, and the person starts again. A device
holding the vault learns the other's model name before anyone confirms (it proved the
vault, so it could read everything anyway). A sync
place that withholds or deletes files stops sync, it cannot change the vault.

Not done: forward secrecy against a later theft of the Master Key. It would add an
X25519 exchange (a new crypto dependency); it protects little here, since everything
sent is already encrypted under that same Master Key.

## Leaks to the cloud provider (stated on the security page)

- How many items, their encrypted sizes (± a few bytes), when they change, how many
  devices. Not names, kinds, contents, tags, or which items are favourites.
- Optional later: pad sizes to buckets to blur them.

## Consequences

- The "nothing goes to the internet" promise becomes "nothing goes to the internet
  unless you turn on Sync, and then only encrypted to your own cloud".
- Export compliance: same algorithms, no change expected; recheck when Sync ships.
- Network code enters the app for the first time: the supply-chain rules
  (`docs/supply-chain.md`, cackle) need a grant for the Google Drive transport.
- One vault in the app (decisions 2026-10-24) keeps the first version simple; the
  format is per vault, so several vaults would sync the same way.

## Plan

1. Core engine + local-folder remote + tests with simulated devices (every row of the
   conflict table, journals, garbage collection, a stalled or rolled-back remote).
2. Google Drive (`drive.file`), Sync settings, joining.
3. P2P on the same Wi-Fi (QR pairing).
4. Content on demand, storage setting, conflict copies in the UI.
